# Что такое wp-dev, какие у нас стенды и есть ли в области лишнее

## 1. Зачем нужна папка `wp-dev/`

`wp-dev/` — это **тестовая инфраструктура проекта**, полностью отделённая от
самого плагина. Плагин (`rvn-compare-products-for-woocommerce/`) — это то, что
получает пользователь; `wp-dev/` — это то, чем я доказываю, что плагин работает.
Без него любая фраза «проверено» была бы голословной.

Ключевая причина существования этой папки: **песочница пересоздаётся между
раундами**. Установленные пакеты, MariaDB, сайты WordPress и `/tmp` стираются —
выживают только файлы рабочей области. Поэтому весь стенд описан кодом и
поднимается двумя командами (`install` → `up`), а не «настроен однажды».

### Что внутри (22 файла, 264 КБ)

| Файл | Размер | Роль |
| --- | --- | --- |
| `stand.sh` | 20.0 КБ | Жизненный цикл стенда: `doctor` (префлайт), `install` (PHP, MariaDB, WP-CLI, Composer, PHPCS/WPCS, PHPStan, Playwright), `up` (новый сайт WP+Woo за ~20 с), `down`, `stop`, `status` |
| `check.sh` | 16.1 КБ | Уровни проверки 0/1/2 и отдельные режимы (`static`, `tests`, `stand`, `front`, `table`, `cache`, `pcp`). Копирует текстовые артефакты прогона в `docs/test-reports/` |
| `docs-check.sh` | 4.7 КБ | Консистентность документации: версия в 3 местах, отсутствие ZIP, отсутствие привязок к фреймворкам, наличие обязательных файлов. Работает без PHP и сети |
| `seed.php` | 12.0 КБ | Демо-магазин: 12 товаров всех типов, 5 категорий, 4 глобальных атрибута |
| `tests/core-logic.php` | 13.9 КБ | Юнит-проверки ядра (лимиты, категории, слияние) — 41 проверка |
| `tests/rest-smoke.py` | 6.0 КБ | REST API: nonce, лимиты, CRUD, слияние — 12 проверок |
| `e2e/frontend-smoke.cjs` | 7.6 КБ | Витрина в браузере: кнопка, счётчик, уведомление, повторный клик — 17 |
| `e2e/table-smoke.cjs` | 4.5 КБ | Страница сравнения, поля, статический шорткод — 7 |
| `e2e/admin-smoke.cjs` | 12.0 КБ | Админка: меню, вкладки, монтирование React, сохранение/сброс — 18 |
| `e2e/cache-regression.cjs` | 16.4 КБ | WP Super Cache: файл кэша, HIT по заголовку, восстановление nonce — 24 |
| `e2e/summary.py` | 1.0 КБ | Сводка JSON-результатов браузерных сценариев |
| `i18n.sh` + `i18n/build-po.py` | 6.8 КБ | POT из исходников → русский PO из словаря → MO + PHP. Ломается, если строка без перевода |
| `i18n/ru_RU.json` | 27.1 КБ | Словарь переводов — **источник истины** для русского языка |
| `admin-ui/src/index.js` | 25.1 КБ | Исходники React-настроек (без JSX, только `createElement`) |
| `admin-ui/build.sh`, `package.json`, `README.md` | 4.4 КБ | Сборка бандла во временном каталоге `/tmp`, чтобы не тащить `node_modules` в область |
| `phpcs.xml.dist`, `phpstan.neon.dist`, `phpstan-bootstrap.php` | 3.4 КБ | Конфиги WPCS и PHPStan 6 (со стабами WP/Woo) |
| `playground.md` | 2.9 КБ | Описание опционального резервного инструмента (см. стенд №4) |

Принцип: **один файл = один режим проверки**. Поэтому ничего из этого не
объединяется — каждый файл вызывается отдельной командой и отвечает за свой
блок результатов.

## 2. Все стенды и когда мы их используем

### Стенд №0 — без стенда (уровень 0, статика)

`bash wp-dev/check.sh level0`

- **Что делает:** синтаксис PHP на 8.1 и 8.3, совместимость точек входа с
  PHP 7.0+, WPCS + Security (0 ошибок и 0 предупреждений), PHPStan уровня 6,
  актуальность POT и полнота русского перевода.
- **Когда:** после **каждого** изменения PHP/JS/CSS. Это самый дешёвый барьер —
  ловит опечатки и нарушения стандартов до любого запуска сайта.
- **Требует:** только PHP и WP-CLI (профиль `install --php=8.1,8.3 --browsers=none`).

### Стенд №1 — `main` (основной)

`bash wp-dev/stand.sh up --name=main` → `http://127.0.0.1:8080`

- **Конфигурация:** новейший WordPress + новейший WooCommerce + PHP 8.3, `en_US`,
  порт 8080, засеянный магазин, плагин подключён символической ссылкой и активен,
  установлен Plugin Check. Последний реальный запуск: **WP 7.1.2 + WC 11.1.2 +
  PHP 8.3.35**.
- **Когда:** уровень 1 (`check.sh level1`) — перед передачей сборки вам;
  регрессия кэша (`check.sh cache`, WP Super Cache ставится именно сюда);
  первая половина уровня 2.
- **Что на нём гоняется:** юнит-тесты, REST, все браузерные сценарии
  (витрина, таблица, админка), активация, работа без WooCommerce, uninstall,
  WP_DEBUG, Plugin Check.

### Стенд №2 — `min` (минимально поддерживаемый)

`bash wp-dev/stand.sh up --name=min` → `http://127.0.0.1:8081`

- **Конфигурация:** WordPress 6.6.x + WooCommerce 9.0.x (новейший патч ветки
  определяется автоматически при первом запуске) + PHP 8.1, **ru_RU**, порт 8081.
- **Когда:** уровень 2 (`check.sh level2`) — перед версионным тегом и перед любым
  изменением, затрагивающим совместимость (заголовки, хуки, новые API).
  Держит нижнюю границу заявленной поддержки: если что-то сломалось на 6.6/9.0/
  8.1 — пользователь на старой сборке это увидит.
- **Что на нём гоняется:** юнит-тесты, REST, витрина, таблица, активация,
  uninstall (Plugin Check достаточно одного раза на `main`).

### Стенд №3 — произвольные метки (`--name=...`)

- **Конфигурация:** сколько угодно параллельных сайтов, у каждого своя база
  (`wp_stand_<имя>`) и свой порт.
- **Когда:** тематическая матрица на финальном этапе перед каталогом
  (Storefront, Twenty Twenty-Five, Astra, Kadence, Blocksy, Hello Elementor —
  **по одной теме на стенд**, никогда все сразу) и разовое воспроизведение
  чужого баг-репорта в изоляции.
- **Сейчас:** не поднято ни одного, лишних демонов нет.

### Стенд №4 — WordPress Playground (резервный, опциональный)

- **Что это:** WordPress в браузере (PHP, скомпилированный в WASM). Ни сервера,
  ни MariaDB, ни системных пакетов. Описан в `wp-dev/playground.md`.
- **Когда:** только если `stand.sh doctor` сообщил, что настоящий стенд
  невозможен, либо для быстрой демонстрации. **Только информативно**: не может
  превратить красный уровень в зелёный и не попадает в отчёты как доказательство.
  Не годится для MariaDB/HPOS, кэша, производительности, Plugin Check.

### Не стенды, но тоже места проверки

- **Ваш живой тестовый сайт** (`http://h607951395.nichost.ru/`, Storefront 4.6.2,
  OpenResty, PHP 8.3.33, WP Super Cache, HPOS) — **ручная** проверка. Полный
  регрессионный чек-лист на 23 пункта пройдёт там в конце версии 0.5.0 (ваше
  решение — вместо мини-проверок по раундам).
- **Приложение-превью в этом чате** — не средство проверки вовсе. Оно только
  показывает этот файл (`docs/ANSWER.md`), относится к песочнице и никогда не
  переносится между чатами.

### Итоговая таблица «когда что запускать»

| Событие | Что запускаю |
| --- | --- |
| Начало раунда с стендом | `doctor` → `install` (профиль по уровню) |
| Любое изменение кода | `check.sh level0` |
| Готовый кусок работы перед показом вам | `check.sh level1` (стенд `main`) |
| Релиз / изменение совместимости | `check.sh level2` (`main` + `min` + кэш) |
| Правки документации | `docs-check.sh` |
| Конец раунда | `stand.sh stop` (серверы + MariaDB, скрипт сам доказывает чистоту) |

Движок браузера по умолчанию Chromium; `--browser=webkit` — опционально в
отдельном раунде (в уровне 2 это приятное дополнение, не обязательное).

## 3. Есть ли в рабочей области лишнее

### Реальные цифры

| Зона | Файлов | Размер | Переносится между чатами |
| --- | --- | --- | --- |
| Плагин | 59 | 684 КБ | да |
| `wp-dev/` | 22 | 264 КБ | да |
| `docs/` | 29 | 292 КБ | да |
| Корень (`AGENTS.md`, `README.md`, `CHANGELOG.md`) | 3 | 29 КБ | да |
| **Итого переносимая область** | **113** | **~1.3 МБ** | **да** |
| `node_modules/`, `.next/`, `src/`, конфиги сборки | — | 675 МБ + 6.6 МБ | **нет**, остаются в песочнице |

Проверено: в переносимой области **нет** ZIP-архивов, скриншотов (они только
перечисляются в `screens-list.txt`), `playground-blueprint.json` и прочих
артефактов. Единственный бинарный файл — `languages/*.mo`, и он там по замыслу
(см. пункт 4 ниже).

**Вывод по вашей гипотезе:** 113 файлов на 1.3 МБ — это очень мало, и это
примерно тот же объём, что был в предыдущих чатах (там было ~187 файлов /
2.2 МБ, из которых половина — не перенесённые сейчас отчёты). 675 МБ
`node_modules` между чатами **не путешествуют** — они ставятся заново в каждой
песочнице. Так что поломку прошлых чатов я по-прежнему объясняю длиной самой
истории диалога, а не количеством файлов. Отказ от переноса 54 файлов отчётов
(328 КБ) был правильным решением с точки зрения порядка, но вряд ли именно он
спас этот чат.

### Что можно пожертвовать (по убыванию пользы)

1. **`docs/test-reports/0.4.1/runs/level1-20260926-095919/`** — 12 файлов,
   17 КБ. Это сырой лог моего прогона уровня 1 в раунде 25, для **закрытой**
   версии 0.4.1. Единственные ценные находки (два дефекта) уже записаны в
   `STATUS.md` и `LOG.md` и попадут в отчёт 0.5.0. Рекомендую удалить.
2. **Разделить `docs/LOG.md`** (37.7 КБ, самый большой документ, растёт каждый
   раунд). Оставить в `LOG.md` только историю текущей версии 0.5.0, а раунды
   0.1.0–0.4.1 перенести в `docs/archive/LOG-archive.md`. Байты почти не
   сэкономим, но **уменьшится самый часто читаемый файл** — а я читаю его каждый
   раунд. Рекомендую сделать.
3. **Сократить `docs/DECISIONS.md`** (30.9 КБ) до перечня действующих решений
   (~10 КБ). Это полный оригинал на русском, тогда как остальные документы —
   сжатые английские пересказы. История останется в старом репозитории.
   Средняя польза: удобно, но не срочно.
4. **Удалить `languages/*.mo`** (31 КБ, единственный бинарник) — уже **запланировано**
   в раунде F (0.5.0): WordPress 6.6+ читает `l10n.php`, а `.mo` нужен только
   более старым версиям, поддержку которых мы поднимаем. Делать это надо вместе
   с подъёмом заголовков, не раньше.
5. **`docs/archive/`** (6 ответов, ~39 КБ). Уже чистился один раз (раунды 05–19
   удалены). Можно оставить только последние 2–3 ответа. Польза небольшая.

### Что объединять не стоит (и почему)

- **`assets/admin/settings.js` (15 КБ) в плагине + исходники в
  `wp-dev/admin-ui/src/`** — дублирование намеренное: собранный бандл лежит в
  плагине, чтобы стенд и ваш сайт работали **без** шага сборки. Если его
  убрать, каждый прогон уровня 1 будет тянуть `@wordpress/scripts` (~200 МБ
  загрузки) — дороже во много раз, чем 15 КБ в области.
- **`wp-dev/i18n/ru_RU.json` (27 КБ) и сгенерированный `.po` (47 КБ)** — JSON
  это источник, PO генерируется из него. Теоретически PO можно не хранить, но
  он нужен переводчикам и обзору — оставляем.
- **Пять файлов `e2e/` + два файла `tests/`** — каждый соответствует своему
  режиму `check.sh` и своему блоку отчёта. Слияние сломает возможность запуска
  одной проверки изолированно (а это спасало, когда «front» был флейки).
- **Три конфига (`phpcs.xml.dist`, `phpstan.neon.dist`, `phpstan-bootstrap.php`)** —
  разные инструменты, 3.4 КБ суммарно.

Единственная косметика, которую я вижу: `wp-dev/playground.md` — это
документация, а не инструмент, и по логике ей место в `docs/`. Но перенос
ломает правило «инструменты в `wp-dev/`» и две ссылки — пользы почти нет,
оставил бы как есть.

### Предлагаемое правило гигиены (на будущее)

Если хотите, зафиксирую в `AGENTS.md`: «в `docs/test-reports/` хранится только
отчёт текущей версии и последний сырой прогон; сырые прогоны закрытых версий
удаляются при закрытии версии, архив ответов — максимум 3 файла». Это держит
область примерно на текущих 110 файлах независимо от количества раундов.
